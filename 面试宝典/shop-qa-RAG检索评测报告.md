# RAG 检索优化评测报告

**项目**：黑马点评·店铺智能问答（`services/shop-qa`，FastAPI + Milvus + BGE-M3）
**评测目的**：量化「混合检索（稠密+稀疏）」相对单路检索的优化幅度，产出可写入简历、可在面试中复现答辩的数据
**评测日期**：2026-11-14
**结论速览**：在全量普查基准（64 条口语化 query × 100% 知识库覆盖）上，混合检索较纯稠密基线 **hit@1 +3.1pp、MRR@10 +1.6pp、nDCG@5 +1.2pp，检索延迟仅 +1ms**；在第一轮设备手册语料上该提升达 **hit@1 +10pp、MRR +7.8pp**。同时评测量化出 **CPU 侧 rerank 精排 p50=33s 且无精度增益**，为精排降级改造提供了数据依据。

---

## 一、评测设计

### 1.1 为什么是「全量普查」而不是抽样

知识库经导入 64 份店铺文档后共 64 条 chunk。本次评测为每条 chunk 构造一条口语化 query，**覆盖率 100%，无采样偏差**——比「100 条抽样」更硬：所有结论对整个知识库成立，不存在「样本没抽到」的质疑空间。

### 1.2 金标构造（自检索法 + 人工口语化改写）

1. 每条 chunk 自动生成「标题腔」草稿 query（规则式，零 LLM 消耗）；
2. 逐条人工改写为点评 APP 用户真实提问风格，分两类：
   - **店名型**（30 条）：含店名，如「新白鹿餐厅运河上街店的店铺信息帮我介绍一下」；
   - **品类+位置型**（34 条）：不含店名，如「湖滨商圈有什么氛围好的酒吧推荐？」——考察语义泛化能力；
3. 金标 = 派生源 chunk 的 `chunk_id`。

### 1.3 消融矩阵（6 配置）

| 配置 | 说明 |
|---|---|
| dense_only | 纯稠密向量（BGE-M3 dense，COSINE）——基线① |
| sparse_only | 纯稀疏向量（BGE-M3 sparse，IP）——基线② |
| hybrid_w_50_50 | 混合检索，WeightedRanker(0.5, 0.5) |
| hybrid_w_80_20 | 混合检索，WeightedRanker(0.8, 0.2)——生产配置 |
| hybrid_rrf | 两路各取 Top10，加权 RRF(k=60) 融合（与生产 node_rrf 同公式） |
| hybrid_w_80_20_rerank | 生产配置 + BGE-reranker-large 精排 Top10 |

### 1.4 公平性控制

- 每条 query 只向量化一次，6 配置共享同一向量（排除向量化波动）；
- 混合配置直接调用生产代码 `milvus_utils.hybrid_search`，测的就是线上行为；
- 统一召回深度（每路 10 条）与金标集；
- 延迟只计检索链路（`perf_counter` 包住 Milvus 调用），p50/p95 统计。

## 三、关键发现

**发现 1：混合检索稳定优于单路，且延迟代价可忽略。**
两轮实验、两种语料上，混合检索的 hit@1 / MRR / nDCG 全面 ≥ 单路最优：设备手册语料上 hit@1 +10pp（83.3%→93.3%），店铺语料上 +3.1pp（93.75%→96.88%）；检索延迟仅从 5ms 增至 6ms。

**发现 2：提升幅度与语料类型强相关——这本身就是调参依据。**
店铺语料（店名/商圈等强关键词）上稀疏路本身很强（96.88%），混合的边际收益收窄；而设备手册语料上收益高达 +10pp。说明**融合权重应按语料类型标定**，不能全局一套：设备手册场景 0.5:0.5 最优，店铺场景 0.5:0.5 与 0.8:0.2 打平。这正是「权重用评测跑出来而不是拍脑袋」的证据。

**发现 3：hit@5 全线 100%，质量差异集中在 Top1 排序——rerank 的收益窗口变窄。**
库内候选少（64 条）时召回深度充足，排序质量（hit@1/MRR）才是差异点。而 CPU 上的 BGE-reranker-large 精排 10 候选 **p50=33s（约为检索延迟的 5500 倍）且 hit@1 无增益（95.31% < 96.88%）**——为「精排降级 / reranker 替换 / 上 GPU」提供了量化决策依据。

**发现 4（诚实披露）：单一金标在多相关文档场景存在低估。**
3 条酒吧类 query（「湖滨商圈有什么氛围好的酒吧推荐？」）在所有配置上 hit@1 均失败——因为商圈内有多家酒吧 chunk 语义同等相关，Top1 命中的是另一家酒吧（业务上仍是好答案），但单金标只认派生源。该局限已通过 hit@3/MRR 缓解（这类 query 在 hit@3 上均命中）。

## 五、面试防守要点

1. **金标怎么来的？** 自检索法（query 由 chunk 内容派生）+ 人工逐条口语化改写，64 条覆盖 100% 知识库，无采样偏差；
2. **样本量够吗？** 不是抽样而是全量普查，结论对整个知识库成立；且做了两轮跨语料实验验证方向一致；
3. **为什么提升只有 3.1pp？** 语料类型决定边际收益：店铺名/商圈是强关键词信号，稀疏单路已很强；设备手册语料上同样的框架测得 +10pp——两组数据放在一起恰恰说明评测在起作用（能区分语料差异）；
4. **rerank 33s 说明什么？** 不是 rerank 模型不好，是 CPU 推理 + 每候选一次前向的代价；数据支持三个方向：换 GPU / 轻量 reranker / 小库场景直接砍掉精排；
5. **单一金标局限？** 主动披露多相关文档场景（同商圈多家酒吧）的单金标低估问题，已用 hit@3/MRR 缓解，下一步可引入多金标标注。
