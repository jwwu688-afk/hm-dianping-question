# 简历条目详解（一）：登录校验与登录态续期

> **简历原文**：登录校验与登录态续期：随机 Token + Redis Hash 分布式登录态；双层拦截器分离「续期」与「校验」，ThreadLocal 保存用户上下文并随请求结束清理，杜绝线程池复用导致的用户串号。

---

## 一、由来背景

**业务起点**：黑马点评是一个类似大众点评的项目，几乎所有接口（查看商铺、下单、点赞）都需要知道「当前是谁在操作」，登录态是全项目最先要解决的基础设施。

**为什么不用原生 Session**：
- Tomcat 原生 Session 把登录态存在**单机内存**里，一旦横向扩容到多台服务（分布式集群），用户的请求被负载均衡分到另一台机器，Session 里就没有他的信息了——「分布式登录态」要解决的就是这个问题；
- 解决思路：登录态从「服务器内存」搬到「所有服务实例都能访问的公共存储」——Redis。服务器变成无状态，任何一台实例拿 Token 查 Redis 都能得到同一个用户。

**为什么是 Token 而不是 sessionId**：Session 机制依赖 Cookie 里的 JSESSIONID 与服务端内存绑定；Token 方案下登录凭证是我们自己生成、自己管理的随机串，与服务器实例无关，天然支持集群与 App/小程序等多端。

---

## 二、完整流程步骤

### 阶段一：发送验证码
1. 前端提交手机号 → 后端 `RandomUtil.randomNumbers(6)` 生成 6 位验证码；
2. 写入 Redis：`login:code:{手机号}` → 验证码，**TTL 2 分钟**（常量 `LOGIN_CODE_TTL`）——短 TTL 防止验证码被暴力枚举。

### 阶段二：登录（校验 + 签发 Token）
3. 用户提交手机号 + 验证码 → 与 Redis 中保存的比对；比对通过即视为登录成功；
4. 判断用户是否存在：`SELECT` 手机号查 `tb_user`，不存在则注册新用户（随机昵称 + 默认头像）；
5. 生成**随机 Token**（UUID），将用户信息裁剪为轻量的 `UserDTO`（只含 id、昵称、头像——不把手机号等敏感字段放进缓存）；
6. `UserDTO` 各字段以 **Hash 结构**写入 Redis：key = `login:token:{token}`，TTL 按 `LOGIN_USER_TTL` 配置；
7. 把 Token 返回给前端，前端存储并在后续每个请求的 Header 中携带。

### 阶段三：请求校验与续期（双层拦截器）
8. **外层拦截器 `RefreshTokenInterceptor`**（拦截所有路径 `/**`，order 排在最前）：
   - 从 Header 取 Token → `entries()` 读取 Hash → `BeanUtil.fillBeanWithMap` 还原为 `UserDTO`；
   - `UserHolder.saveUser(userDTO)` —— 存入 **ThreadLocal**；
   - **刷新 TTL**（`expire(key, TTL)`）—— 只要用户仍在活跃访问，登录态就一次次被续命，实现「无感续期」：活跃用户永远不会被登出，只有长时间不访问才会自然过期；
   - 无论是否登录都放行（外层不拦截，只负责准备工作）。
9. **内层拦截器 `LoginInterceptor`**（拦截需要登录的业务路径，order 靠后）：
   - 只做一件事：`UserHolder.getUser() == null` 则拦截返回 401「请先登录」，否则放行。
   - 职责分离的原因：如果把「刷新 TTL」和「校验」放在同一个拦截器里，未登录用户（如访问首页）也会走到校验逻辑，逻辑纠缠；拆开后外层管「准备 + 续期」，内层管「要不要拦」。

### 阶段四：请求结束清理
10. `afterCompletion()`（请求完全结束时执行）调用 `UserHolder.remove()` 清除 ThreadLocal——这一步是**并发安全的关键**，见下文术语解释。

## 三、专业名词逐一解释

| 术语 | 确切含义 |
|---|---|
| **随机 Token** | 登录成功后生成的不可预测随机串（UUID），作为 Redis 中登录态的 key，也是客户端后续请求的凭证。相比「手机号当 key」，随机串不可伪造、不可枚举 |
| **分布式登录态** | 登录信息存在所有服务实例共享的 Redis 中（而非单机 Session 内存），多实例集群下任何节点都能校验同一份登录态 |
| **Redis Hash** | 哈希表结构：一个 key 下存多个 field-value 对。此处 `login:token:{token}` 下有 name、id 等字段。相比把整个对象序列化成一个大 String，Hash 支持按字段读写、字段增删不用整包覆盖 |
| **TTL** | Time To Live，key 的剩余存活时间。到期 Redis 自动删除该 key——登录态过期机制、验证码防爆破都靠它 |
| **无感续期** | 用户每次请求都把登录态 TTL 重置回满值，活跃用户不感知任何「即将过期」，只有持续不访问才自然登出 |
| **拦截器（Interceptor）** | Spring MVC 的请求拦截组件，在 Controller 前后执行 `preHandle / postHandle / afterCompletion`。与 Servlet 过滤器（Filter）相比，拦截器能拿到 Handler 信息、由 Spring 管理、可指定 order 排序 |
| **双层拦截器** | 两个拦截器按 order 链式执行：外层（`/**` 全拦截）负责「读取用户 + 刷新 TTL + 写 ThreadLocal」，内层只负责「校验并拦截」。分层让未登录的公开接口也能享受 TTL 续期 |
| **ThreadLocal** | 线程本地变量：每个线程有独立的一份存储，互不干扰。此处把当前用户绑定到「正在处理这个请求的线程」上，Controller/Service 里随时 `UserHolder.getUser()` 取用，不用层层传参 |
| **线程池复用与用户串号** | Tomcat 的工作线程用完不销毁、回收复用。若请求 A 结束后不清 ThreadLocal，线程被复用去处理请求 B 时，B 会读到 A 的用户——「串号」事故。所以 afterCompletion 必须清理 |
| **afterCompletion** | 拦截器生命周期最后一步，无论请求成功还是抛异常都会执行，是清理资源的标准位置 |
| **401** | HTTP 状态码 Unauthorized，表示未登录或凭证无效 |
| **UserDTO** | 数据传输对象：只含 id/昵称/头像的瘦身版用户。避免把手机号等敏感信息存进 Redis、也减小缓存体积 |

## 四、如何测试验证（方法与过程）

本条**没有跑性能压测基线**，原因是：登录校验是单次 O(1) 的 Redis 读 + 内存操作，延迟在微秒~毫秒级，瓶颈不可能出现在这里，压测意义有限。它的验证分三层：

### 4.1 源码审计（参数与结构核对）
- 核对 `RedisConstants`：`LOGIN_CODE_TTL = 2 分钟`、登录态 key 前缀 `login:token:`、TTL 常量——与简历中「2min TTL」「随机 Token」表述一一对应；
- 核对两个拦截器的 order 顺序与各自拦截路径（外层 `/**`，内层仅业务路径）；
- 核对 `afterCompletion` 中确有 `UserHolder.remove()`。

### 4.2 功能自测（Postman / 前端页面）
1. 发验证码 → Redis 中可见 `login:code:{phone}` 且 2 分钟后自动消失（TTL 生效）；
2. 登录 → 返回 Token，Redis 中出现 `login:token:{token}` 的 Hash；
3. 带 Token 请求业务接口 → 200；不带 Token 请求受保护接口 → 401；
4. 连续多次请求后用 `TTL login:token:{token}` 观察 → 每次请求后 TTL 重置回满值（无感续期生效）；
5. 停止访问超过过期时长 → key 消失，再请求即 401（自然过期生效）。

### 4.3 并发安全验证（ThreadLocal 清理的必要性）
- 反证实验：注释掉 `afterCompletion` 中的清理代码，用两个不同账号交替快速请求 → 偶发出现「B 请求读到 A 的用户」（线程池把 A 用过的线程分给了 B）；
- 恢复清理代码后该现象消失。这就是简历里「杜绝线程池复用导致的用户串号」的实验依据。

### 4.4 如需补充性能基线（可选扩展）
若未来想加数字，可测：登录态校验的单请求延迟（Redis Hash 读取约 0.5~1ms）、1000 并发登录态查询的 QPS 与 Redis CPU 占用，框架可直接复用本项目 `benchmark/` 下的多线程基准模式。

## 五、面试防守要点

1. **「为什么拦截器要拆两层？」**——外层 `/**` 全拦截做续期（公开接口也要保活登录态），内层只拦业务路径做校验；合在一起未登录用户也会触发续期逻辑，职责纠缠；
2. **「ThreadLocal 为什么会串号？」**——Tomcat 线程池复用线程，ThreadLocal 的值跟着线程走而不跟着请求走，必须 afterCompletion 手动清；
3. **「Token 泄露怎么办？」**——可加服务端 TTL 缩短 + 更换 Token 频率、绑定设备指纹；本项目按教学范围未做，如实回答；
4. **「TTL 具体多少？」**——验证码 2 分钟是硬编码常量；登录态 TTL 是配置常量（源码中数值可调），核心机制是「每次请求重置」而非具体数值。
