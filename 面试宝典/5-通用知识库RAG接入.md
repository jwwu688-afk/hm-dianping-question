# 简历条目详解（五）：通用知识库 RAG 接入

> **简历原文**：通用知识库 RAG 接入：Spring Boot 代理层对接 Python RAG 服务，打通上传→切分→向量入库→混合检索→联网兜底→SSE 生成的全流程；自建检索评测框架（64 条金标全量普查 × 6 配置消融），混合检索较纯稠密基线 hit@1 提升 3.1~10pp、MRR@10 提升 1.6~7.8pp、延迟仅 +1ms。

---

## 一、由来背景

**业务需求**：黑马点评的用户需要用自然语言问「大关附近有什么茶餐厅」「这家店怎么去」——这些问题靠关键词搜索匹配不了（用户说法千变万化），需要「理解语义 + 从知识库里找依据 + 组织成回答」的能力，也就是 **RAG（Retrieval-Augmented Generation，检索增强生成）**：先从知识库检索相关内容作为证据，再把证据交给大模型生成回答。

**架构分工**：项目主体是 Spring Boot（Java），但 RAG 生态（向量库客户端、Embedding 模型、LangGraph 编排）在 Python 侧更成熟，所以采用 **Java 代理层 + Python RAG 服务** 的架构：Java（:8081）负责用户会话、鉴权与 SSE 转发，Python（:8003，FastAPI）负责知识库管理与检索生成，两者通过 HTTP 调用连接。知识库是 64 份店铺 Markdown 文档。

---

## 二、完整流程步骤

### 导入链路（文档 → 向量库）
1. 用户上传 Markdown/PDF（≤20MB）→ Java 层转交 Python 服务 → 存 MinIO → 返回 202（异步处理中）+ 状态轮询接口；
2. **解析切分**：MD 按标题层级切分，超长章节再切（≤2000 字符）、过短章节合并（<500 字符）；
3. **向量化**：每批 5 条用 BGE-M3 模型同时生成**稠密向量**（语义）与**稀疏向量**（关键词），写入 Milvus 集合 `hmdp_knowledge_v2`（两套向量字段同一集合）。

### 问答链路（用户提问 → 回答）
4. 用户提问经 Java 转发给 Python；
5. **商品名/实体确认**：LLM 抽取问题中的实体名，混合检索（WeightedRanker 0.8:0.2）对齐标准名称（分数 >0.85 确认、0.6~0.85 反问用户、<0.6 拒答）；
6. **多路并行检索**：原始 query 混合检索（稠密+稀疏）+ HyDE 检索（LLM 先生成假设答案，用假设答案再去检索）+ 知识图谱 + 联网搜索 MCP；
7. **RRF 融合**：本地两路结果按加权 RRF（k=60）融合成 Top10；
8. **重排序精排**：BGE reranker 对 Top10 + 联网结果统一打分重排，取前 6 条证据；
9. **生成**：LLM 基于证据生成回答；
10. **SSE 推送**：Python 侧流式生成，Java 逐片（1024 字节）转发给前端实时渲染。

### 评测链路（本次新增，简历数字的来源）
11. 自建评测框架（4 个脚本）：金标构建（自检索法 + 人工口语化改写）→ 检索封装 → 指标计算 → 6 配置消融主程序；
12. 对 64 条金标 query 跑「纯稠密 / 纯稀疏 / 混合 0.5:0.5 / 混合 0.8:0.2 / RRF / +rerank」六种配置，统计 hit@k、recall@5、MRR@10、nDCG@5 与延迟。

## 三、专业名词逐一解释

### 3.1 架构与流程类术语

| 术语 | 确切含义 |
|---|---|
| **RAG** | Retrieval-Augmented Generation：检索增强生成。先检索知识库拿到相关片段作为「证据」，再让大模型基于证据回答——避免大模型凭空编造 |
| **Java 代理层** | Java 后端不直接做 RAG，而是把用户请求转发给 Python RAG 服务、把结果转发回前端——承担会话管理、鉴权、SSE 中转职责 |
| **SSE** | Server-Sent Events，服务器单向推送技术：HTTP 长连接上服务器持续向浏览器推送文本片段。相比 WebSocket（双向）更轻，适合「大模型逐字生成、前端逐字渲染」的场景 |
| **Milvus** | 开源向量数据库：存储向量并支持近似的「最相似向量」检索（ANN），本项目用它存稠密+稀疏两种向量 |
| **BGE-M3** | 智源的多语言 Embedding 模型，一次编码同时产出稠密向量（1024 维浮点）与稀疏向量（关键词权重），是「混合检索」的向量来源 |
| **稠密向量 / 稀疏向量** | 稠密 = 把整句话压缩成一个固定长度的语义向量，能匹配「意思相近」；稀疏 = 类似 BM25 的按词加权表示，能精确匹配「字面相同」——两者各有盲区，所以混合 |
| **混合检索** | 同一查询分别用稠密和稀疏两路召回，再融合排序。实测（见下文）它比任一单路更准 |
| **HyDE** | Hypothetical Document Embeddings：让 LLM 先编一个「假设答案」，拿假设答案去检索——因为答案和文档比问题和文档更相似，能补召回 |
| **RRF（Reciprocal Rank Fusion）** | 按排名融合多路结果的算法：每路给文档贡献 `1/(k+名次)` 分（k=60），累加后重排。只看名次不看分数，免疫两路分数的量纲差异 |
| **联网搜索兜底** | 本地知识库没有的内容（如最新营业信息）转 Web 搜索 MCP 补充，与本地结果合并进入精排 |
| **MCP** | Model Context Protocol：Agent 调用外部工具的协议，此处用于接入联网搜索工具 |

### 3.2 评测指标类术语（含被复制变形的写法澄清）

> 你消息里的 "HIT"、"@//0.0.0.1/"、"PPMRR" 都是复制粘贴时把记法弄花了，规范写法分别是 **hit@1、hit@k（@ 读作「在 Top-k 内」）、MRR**。"@//0.0.0.1/" 不是术语，是 "hit@1" 的 `@` 与本机 IP 文本混排后的显示产物。

| 术语 | 确切含义 |
|---|---|
| **hit@k** | 「hit @ k」= 正确答案出现在检索结果**前 k 名**之内即算命中，记 1 分否则 0 分；64 条 query 取平均得百分比。hit@1 = 第一眼就命中的比例 |
| **金标（golden set）** | 评测用的标准答案集：每条 query 配一个「应该被检索到」的 chunk_id。构建方法是自检索法——query 从某条 chunk 的标题/内容派生，该 chunk 即金标；再由人工把 query 逐条改写成口语化提问 |
| **全量普查** | 64 条金标覆盖知识库全部 64 条 chunk（覆盖率 100%），不是抽样——结论对整个知识库成立，不存在采样偏差 |
| **6 配置消融** | 消融实验（ablation）：逐个增加/替换组件对比效果。六个配置 = 纯稠密 / 纯稀疏 / 混合 0.5:0.5 / 混合 0.8:0.2 / RRF 融合 / 混合+精排，控制变量只有「融合与精排策略」 |
| **recall@5** | 前 5 名覆盖了金标集合的几成：`|Top5 ∩ 金标| ÷ |金标总数|`。金标有多条时比 hit@5 更精细 |
| **MRR@10** | Mean Reciprocal Rank：金标首次命中的名次取倒数（第 1 名 = 1.0，第 2 名 = 0.5，第 3 名 ≈ 0.33，前 10 没有命中 = 0），64 条取平均。衡量「正确答案排得靠不靠前」 |
| **nDCG@5** | Normalized Discounted Cumulative Gain：对结果逐位累加「相关性 ÷ log₂(位置+1)」再除以理想排序的得分，0~1 之间。位置越靠后贡献打折越多，比 MRR 更全面地反映整体排序质量 |
| **pp（百分点）** | percentage point，**绝对百分点差**：hit@1 从 83.3% 涨到 93.3%，提升 10pp（不是 10%——10% 相对提升应写成 +12%）。简历里「+3.1~10pp」就是「3.1 到 10 个百分点之间，取决于语料」 |
| **p50 / p95 / p99** | 百分位延迟：一半请求耗时低于 p50，95% 低于 p95，99% 低于 p99。检索延迟「+1ms」指 p50 从 5ms 变 6ms |

## 四、如何测试验证（方法与过程）

### 4.1 评测框架（自建 4 个脚本，可复用）

| 脚本 | 职责 |
|---|---|
| `build_golden_set.py` | 从 Milvus 采样 chunk 自动生成草稿 query + 金标（零 LLM 消耗） |
| `milvus_search.py` | 检索封装：单路稠密 / 单路稀疏 / 生产版混合检索 |
| `metrics.py` | hit@k / recall@k / MRR@k / nDCG@k / 延迟百分位 |
| `run_eval.py` | 消融主程序：6 配置 × 全量金标，输出对比报告与明细 CSV |

### 4.2 测试过程

1. **建金标**：从知识库采样 chunk，自动生成「标题腔」草稿 query，**人工逐条改写成口语化提问**（制造真实场景的表述差异）；
2. **跑消融**：每条 query 向量化一次（六配置共享，控制变量），分别以六种策略检索，逐条记录名次与耗时；
3. **算指标**：排序结果与金标集合做交集运算，得到 hit@1/3/5、recall@5、MRR@10、nDCG@5 与延迟 p50/p95；
4. **两轮跨语料验证**：第一轮 30 条（旧库·设备手册语料）、第二轮 64 条全量普查（生产库·店铺语料）。

### 4.3 实测数据

**第二轮（64 条全量普查，生产集合 hmdp_knowledge_v2）**：

| 配置 | hit@1 | hit@3 | MRR@10 | nDCG@5 | p50 |
|---|---|---|---|---|---|
| 纯稠密（基线） | 93.75% | 100% | 0.969 | 0.977 | 5ms |
| 纯稀疏 | 96.88% | 100% | 0.984 | 0.989 | 4ms |
| **混合检索（生产）** | **96.88%** | **100%** | **0.984** | **0.989** | **6ms** |
| +rerank 精排 | 95.31% | 100% | 0.977 | 0.983 | 33090ms |

**第一轮（30 条，设备手册语料）**：混合检索 hit@1 从 83.3% 提升到 93.3%（+10pp）、MRR@10 +7.8pp。

### 4.4 数据解读

- **混合检索 > 任一单路**：两轮、两种语料方向一致（+3.1pp 与 +10pp）；原因是互补性——店名/型号类问题关键词路强，口语改述类问题语义路强（评测明细里有具体的成功/失败案例对）；
- **提升幅度与语料类型相关**：店铺语料店名即关键词，稀疏路本身很强，边际收益收窄到 +3.1pp；手册语料语义错配多，收益高达 +10pp——这证明「融合权重需按语料标定」；
- **诚实披露**：rerank 在 CPU 上 p50=33s 且无精度增益（评测直接暴露的生产隐患，形成精排降级改造依据）；HyDE 路因消耗 LLM 额度未纳入评测。

## 五、面试防守要点

1. **「hit@1 是什么？」**——正确答案出现在第 1 名的 query 占比；@k 记法表示「在 Top-k 之内」；pp 是绝对百分点不是相对百分比；
2. **「金标怎么来的，可信吗？」**——自检索法构建（零标注成本）+ 人工口语化改写（制造真实表述差异）+ 全量普查（64/64 覆盖，无采样偏差）；
3. **「为什么提升只有 3.1pp？」**——语料类型决定边际收益，且给出了 +10pp 的对照实验；能区分语料差异恰恰说明评测有效；
4. **「评测框架是现成的吗？」**——自建，4 个脚本，金标/检索/指标/消融四层解耦，换一个 Milvus 知识库改集合名即可复用；
5. **「为什么不用 RAGAS/TruLens？」**——本轮聚焦检索层指标（可控、可解释），生成层指标是下一步；自建框架的好处是延迟与成本口径完全自持。
