# 简历条目详解（三）：秒杀异步削峰（MQ 消融实测）

> **简历原文**：秒杀异步下单：预扣成功后经 RabbitMQ 异步落库，接口响应不依赖 MySQL 写入；同步落库 vs MQ 异步实测接口侧 p50 降低 23%（381→292ms）、p99 降低 17%（612→508ms），下单压力收敛到 Redis 层。

---

## 一、由来背景

Lua 预扣解决的是「资格发放」的并发正确性，但抢到资格之后订单总要写进 MySQL——如果请求线程自己同步落库，**每个用户都要陪数据库写完才能拿到响应**：

- DB 写入是行锁 + 连接池排队，高峰期 1000 笔请求的写入会挤在请求窗口内瞬时打向 MySQL；
- 用户侧感受到的延迟里混进了大量「别人的 DB 写入排队时间」。

解法是把「资格发放」和「订单落库」解耦：预扣成功后把订单丢进 **RabbitMQ**，接口立刻返回；落库由消费者按自己的节奏慢慢消化。这就是经典的**削峰填谷**：瞬时流量被队列蓄住，DB 按恒定速率消费。

本条简历的基线就是把「同步落库 / MQ 异步落库」在同一并发下做消融实测，量化「不依赖 MySQL 写入」到底省了多少。

---

## 二、完整流程步骤

### 发送侧（生产者，与生产代码一致）
1. 请求到达 → Lua 预扣（同详解二，返回 0 = 拿到资格）；
2. 组装 `VoucherOrder`（订单 ID 由 `RedisIdWorker` 全局唯一 ID 生成器生成）；
3. `rabbit.convertAndSend(EXCHANGE, "", order)` —— 订单以 **JSON**（`Jackson2JsonMessageConverter`，信任包 `com.hmdp.entity`）发送到 **Fanout 交换机** `hmdp.order.fanout.exchange`；
4. Fanout 交换机把消息复制到绑定的队列 `hmdp.order.queue`（durable，重启不丢定义）；
5. **接口立即返回**「排队中」——不等待任何 MySQL 写入。

### 消费侧（消费者，与生产代码一致）
6. `@RabbitListener(queues = QUEUE)` 监听队列（**默认并发度 1**：单消费者串行消费）；
7. 收到消息 → `createVoucherOrder`：扣 MySQL 库存（`UPDATE ... SET stock = stock - 1 WHERE voucher_id = ?`）+ 插入订单（`INSERT INTO tb_voucher_order`）；
8. 超卖由 Redis 层保证（只有拿到资格的 100 笔会进队列），消费者无需再加锁判断。

## 三、专业名词逐一解释

| 术语 | 确切含义 |
|---|---|
| **RabbitMQ** | 消息中间件：接收、存储、转发消息的独立服务。生产者和消费者通过它解耦——互不等待、互不知道对方存在 |
| **异步落库** | 「订单写入 MySQL」不在用户请求的线程里做，而是由 MQ 消费者在其后台线程里做；用户请求只负责把消息投进队列 |
| **同步落库** | 对照方案：用户请求线程在返回响应之前，自己完成 DB 扣库存与插订单——响应时间 = 资格判断 + DB 写入全程 |
| **Exchange（交换机）** | RabbitMQ 的路由枢纽：生产者只把消息发给交换机，由它决定转发到哪些队列 |
| **Fanout 交换机** | 广播型交换机：无视 routing key，把消息复制到所有绑定它的队列。本项目只有一个订单队列，Fanout 为后续多队列扩展预留 |
| **Queue（队列）** | 消息的存储缓冲区，FIFO；durable=true 保证 RabbitMQ 重启后队列定义仍在 |
| **@RabbitListener** | Spring AMQP 的注解式消费者：框架自动拉取队列消息并回调方法。**默认并发度 1**——单线程逐条消费，这正是「削峰」的速率上限 |
| **Jackson2JsonMessageConverter** | 消息体 JSON 序列化器：发送时把 VoucherOrder 对象转 JSON，接收时还原。相比 Java 原生序列化，JSON 可读、跨语言、无反序列化安全风险 |
| **削峰填谷** | 瞬时大量请求先进队列蓄着，消费者按恒定速率处理——把「1000 笔写入同时砸 DB」变成「单消费者匀速写入」 |
| **p50 / p95 / p99** | 百分位延迟：50% 的请求耗时低于 p50，95% 低于 p95，99% 低于 p99。p99 高说明有长尾慢请求 |
| **接口侧延迟** | 用户视角的响应耗时。C1 组含「Lua + DB 落库」全程；C2 组只含「Lua + MQ 发送」——两组的差就是「用户不用陪 DB 等待」省下的时间 |
| **墙钟时间** | 从第一笔请求开始到最后一笔受理/落库完成的物理时钟总耗时 |
| **受理与落库解耦** | 「用户拿到下单资格」与「订单写进数据库」两个阶段彻底分离，中间由队列缓冲——用户的响应时间不再受 DB 波动影响 |

## 四、如何测试验证（方法与过程）

### 4.1 测试工具与设计

- 基准脚本：`src/test/java/com/hmdp/benchmark/SeckillMqBenchmark.java`；
- 两组对照（1000 笔请求 / 券 ID=10 / 库存 100，两组共用同一条 Lua 资格判断，**差异只在预扣成功后怎么落库**）：
  - **C1 同步落库**：Lua 成功后，请求线程自己执行 DB 扣减 + 插订单，返回时已全部落库；
  - **C2 MQ 异步**：Lua 成功后 `convertAndSend` 即返回；由 1 个消费者（复刻生产 `createVoucherOrder` 逻辑）异步落库；
- 消费端复刻生产消费者逻辑，并发度 1 与生产 `@RabbitListener` 默认一致；连接池规格两组相同（50）；
- 公平性：每组实验前重置现场（MySQL 库存/订单清零、Redis 预热、**清空队列残留消息**）。

### 4.2 实测数据

| 方案 | 成功受理 | 接口侧延迟 p50 / p95 / p99 | 墙钟（全部受理） | 落库完成总时长 |
|---|---|---|---|---|
| C1 同步落库（无 MQ） | 100 | 381 / 587 / 612 ms | 673ms | 673ms（受理即全部落库） |
| **C2 MQ 异步（生产）** | 100 | **292 / 490 / 508 ms** | 556ms（受理） | 836ms（全部落库完成） |

C2 落库节奏（削峰曲线）：`210ms:19笔 → 418ms:53笔 → 633ms:81笔 → 836ms:100笔`。

### 4.3 数据解读

- **接口侧 p50 降低 23%（381→292ms）、p99 降低 17%（612→508ms）**：同步组每笔请求都陪 DB 写完才返回；异步组拿到资格即返回——用户不用陪 DB 等待；
- **削峰曲线**：1000 笔瞬时请求的 DB 写入从「瞬时堆积」变成消费端匀速消化，DB 写入峰值被压平；
- **诚实披露**：本轮规模下「全部落库完成」的总时长同步略优（673ms vs 836ms，因为 50 连接池并行写 > 单消费者串行写）——MQ 的核心收益不是总吞吐，而是**用户延迟更低 + DB 压力恒定 + 受理与落库解耦**；并发越高、DB 越忙，同步组的连接池排队会线性恶化，异步组消费速率恒定，差距继续拉大；
- **超卖归 Redis 管**：消费者落库 SQL 不带库存条件也不会超卖——因为只有拿到资格的 100 笔消息会进队列。

## 五、面试防守要点

1. **「异步落库比同步还慢怎么解释？」**——指「全部落库完成」的总时长：单消费者串行确实比 50 连接池并行慢；但 MQ 买的是**用户延迟更低**（p50 -23%）和 **DB 压力恒定**，不是总吞吐；并发越高这个差距越明显；
2. **「消费者挂了怎么办？」**——消息持久化 + 队列 durable，重启后继续消费；按项目教学范围未配生产者确认/死信/重试，如实回答并说明生产化补齐方向（confirm + 手动 ack + 死信队列 + 对账）；
3. **「用户怎么知道最终结果？」**——orderId 返回后轮询订单状态接口（读 Redis），超时按失败处理并回滚 Redis 名额，对账任务兜底；
4. **「为什么接口响应不依赖 MySQL 是卖点？」**——把「用户能不能抢到」与「数据库有多忙」彻底解耦：DB 再慢，抢购接口的响应时间不受影响，用户体验与系统可用性被隔离在队列两侧。
