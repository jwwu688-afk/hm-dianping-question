# Redis 核心功能压测评测报告（秒杀 / 缓存击穿）

**项目**：黑马点评（`hm-dianping`，Spring Boot + MySQL + Redis + RabbitMQ）
**评测目的**：为秒杀与缓存防护方案补上实测基线——同一并发压力下对比不同实现的超卖数量、DB 压力与延迟，产出可写入简历、可复现的数据
**评测日期**：2026-11-14
**结论速览**：1000 并发抢 100 件库存实测——**无锁裸扣 DB 方案库存透支至 -900（900 件超卖、1000 笔订单全部无法兑现）**；**Redis+Lua 方案 0 超卖、受理阶段 MySQL 写入 0 次**；500 并发瞬时击穿实测——**无防护 DB 回源 500 次（p50=992ms），互斥锁回源 1 次（p50=270ms），逻辑过期回源 1 次且全部请求 p50=14ms 秒回**。

---

## 一、评测设计

### 1.1 环境

- Docker 容器：MySQL 8.0（hmdp 库，tb_seckill_voucher / tb_voucher_order / tb_shop）+ Redis 6.2（带认证）+ RabbitMQ
- 压测形式：JUnit 多线程基准（`CyclicBarrier` 栅栏对齐，所有线程同一瞬间发起请求），直接调用生产代码路径
- 隔离控制：每组实验前统一重置现场（MySQL 库存/订单清零、Redis key 清理）；各对照组共用相同规格的数据库连接池（秒杀 50 / 缓存 20，模拟生产连接池上限）

### 1.2 消融矩阵

**实验 A（秒杀）**：券 ID=10，初始库存 100，1000 并发

| 组 | 方案 | 说明 |
|---|---|---|
| A1 | 无锁裸扣 DB | `UPDATE ... SET stock = stock - 1`（不带库存条件）+ 无条件插单——最朴素实现 |
| A2 | CAS 条件更新 DB | `UPDATE ... WHERE stock > 0`，仅扣到库存才插单——靠 InnoDB 行锁串行 |
| A3 | Redis + Lua（生产方案） | 库存校验 + 一人一单 + 预扣在单脚本原子完成，生产 `seckill.lua` 原文执行 |

**实验 B（缓存击穿）**：热点店铺 ID=1，缓存失效瞬间 500 并发涌入

| 组 | 方案 | 说明 |
|---|---|---|
| B1 | 无防护 | `queryWithPassThrough`——所有未命中线程都回源 DB |
| B2 | 互斥锁 | `queryWithMutex`（生产 CacheClient）——SETNX 抢锁，1 线程重建其余自旋等待 |
| B3 | 逻辑过期 | `queryWithLogicalExpire`（生产 CacheClient）——预先写入已逻辑过期的缓存，全部请求拿旧数据、后台单线程异步重建 |

### 1.3 公平性保障

- 混合配置直接调用**生产代码**（`seckill.lua`、`CacheClient`），不是模拟实现；
- 每组实验前重置现场，起点完全一致；
- DB 回源次数用计数器直接统计（B 组），超卖用终态库存直接计算（A 组），不靠推断。

## 二、评测数据

### 实验 A：秒杀消融（1000 并发 / 初始库存 100 / 连接池 50）

| 方案 | 成功受理 | 落库订单 | 终态库存 | 超卖 | 墙钟耗时 | 单请求延迟 p50 / p95 / p99 |
|---|---|---|---|---|---|---|
| A1 裸扣 DB（无库存条件） | 1000 | 1000 | **-900** | **900 件** | 2770ms | 1468 / 2607 / 2705 ms |
| A2 CAS 条件更新 DB | 100 | 100 | 0 | 0 | 402ms | 329 / 355 / 358 ms |
| **A3 Redis+Lua（生产）** | **100** | 0（受理阶段未落库） | 0（Redis） | **0** | 581ms | 306 / 514 / 532 ms |

关键对比：**A1 的 1000 次 UPDATE 与 1000 次 INSERT 全部打在 MySQL**；A2 的 1000 次 UPDATE 同样全部打 DB（行锁竞争），但 SQL 层条件挡住了超卖；**A3 受理阶段 MySQL 写入 0 次**——压力被完整收敛到 Redis 层。

### 实验 B：缓存击穿防护消融（热点店铺 1 / 500 并发 / 连接池 20）

| 方案 | DB 回源次数 | 全部线程返回耗时 | 单请求延迟 p50 / p95 | 行为 |
|---|---|---|---|---|
| B1 无防护 | **500** | 1058ms | 992 / 1022 ms | 每个未命中线程都回源 |
| **B2 互斥锁** | **1** | 304ms | 270 / 283 ms | 仅 1 线程重建（回源时间线证实：单线程 88ms 时刻回源），其余等缓存 |
| **B3 逻辑过期** | **1**（异步后台） | **48ms** | **14 / 19 ms** | 500 请求全部秒回旧数据，后台异步重建 1 次 |

## 三、关键发现

**发现 1：超卖不是理论问题，1000 并发下裸扣 DB 必然透支库存。**
A1 组库存被打到 **-900**：行锁虽然串行化了扣减，但没有条件判断，1000 笔订单全部受理——即超卖 900 件、1000 笔订单中 900 笔注定无法履约。

**发现 2：防超卖的两条路线成本差异清晰可量化。**
A2（CAS 条件更新）靠 SQL 层 `stock > 0` 挡住了超卖，但 **1000 次 UPDATE 全部压到 DB 一行上行锁竞争**；A3（Redis+Lua）把竞争挪到内存级单线程事件循环，**受理阶段 MySQL 零写入**，延迟与 A2 同量级——「压力收敛到 Redis 层」这句话第一次有了实测注脚。

**发现 3：缓存击穿的危害可以用回源次数直接度量。**
B1 组 500 线程无一例外全部回源（DB 瞬时被 500 次查询冲击，单请求 p50 高达 992ms——连接池排队是主因）；B2 互斥锁把回源压到 **1 次**（回源时间线证实仅 1 个线程在 88ms 时刻回源），代价是其余 499 个线程等待重建完成（p50=270ms）；B3 逻辑过期则让全部请求 **p50=14ms 秒回旧数据**，重建在后台完成——**「一致性优先选互斥锁、可用性优先选逻辑过期」不再是一句口号，而是 p50=270ms vs 14ms 的实测权衡**。

**发现 4（方法论披露）**：压测脚本本身踩了两个测试工程陷阱（try-with-resources 中提前执行 executeQuery 导致参数未绑定；连接池连接被 close 而非归还导致线程池饿死），均已修复并在报告中保留复现说明——压测代码的正确性本身就是基线可信的前提。

## 四、简历文案（实测数据版）

**秒杀（升级后）：**

> 优惠券秒杀下单：Redis + Lua 将库存校验、一人一单判断与库存预扣合并为单脚本原子操作（5 类返回码、全部校验前置规避 Lua 运行时错误不回滚问题）；1000 并发抢 100 件库存压测实测——无锁裸扣 DB 方案库存透支至 -900（900 件超卖），CAS 条件更新方案 0 超卖但 1000 次 UPDATE 全部落库行锁竞争，Redis+Lua 方案 0 超卖且受理阶段 MySQL 写入 0 次；预扣成功后经 RabbitMQ 异步落库，接口响应不依赖 MySQL 写入，下单压力收敛到 Redis 层。

**缓存（升级后）：**

> 处理缓存常见问题：以缓存空值（2min TTL）拦截穿透请求；针对热点数据实现互斥锁与逻辑过期两种重建方案并完成 500 并发击穿实测——无防护 DB 回源 500 次（p50=992ms）、互斥锁回源 1 次（p50=270ms，一致性优先）、逻辑过期回源 1 次且全部请求 p50=14ms 秒回旧数据（可用性优先），以实测数据支撑缓存重建策略选型。

**登录（无压测基线，保持可核验参数版）：**

> 实现登录校验与登录态无感续期：短信验证码（2min TTL）+ 随机 Token + Redis Hash 存储登录态；双层拦截器职责分离——外层逐请求刷新 TTL 并将 UserDTO 写入 ThreadLocal、内层仅做校验放行，请求结束在 afterCompletion 清理 ThreadLocal，规避 Tomcat 线程池复用导致的用户串号。

## 五、面试防守要点

1. **压测怎么做的？** JUnit 多线程基准：CyclicBarrier 栅栏对齐让 1000/500 线程同一瞬间发起；每组实验前重置现场；直接调用生产代码（seckill.lua 原文、CacheClient 原方法），不是模拟；
2. **为什么 A2 没超卖还是要用 Lua？** A2 防住了超卖但 1000 次 UPDATE 全部压在 DB 一行上（行锁串行 + 连接池排队）；Lua 把竞争挪到 Redis 内存级，受理阶段 DB 零写入——这就是「MySQL 写入量 1000 → 0」的意义；
3. **互斥锁和逻辑过期怎么选？** 拿数据说话：互斥锁 p50=270ms（等待重建）但返回的必然是新数据；逻辑过期 p50=14ms 但短暂返回旧数据——一致性与可用性权衡被量化成了具体毫秒数；
4. **超卖 900 件怎么算的？** 终态库存 -900 = 初始 100 - 扣减 1000，即 1000 笔订单卖出了 100 份库存之外多出的 900 份；
5. **压测脚本可信吗？** 主动披露测试工程踩坑（executeQuery 提前执行、连接池饿死）与修复过程，原始数据与脚本全部可复现。
