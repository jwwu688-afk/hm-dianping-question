# 简历条目详解（四）：缓存穿透与击穿防护

> **简历原文**：缓存穿透与击穿防护：缓存空值拦截穿透请求；500 并发击穿实测——互斥锁与逻辑过期将 DB 回源次数从 500 压至 1 次，请求 p50 由 992ms 降至 270ms（互斥锁）/14ms（逻辑过期），以实测数据支撑双方案选型。

---

## 一、由来背景

项目里商铺查询是典型的「读多写少」场景：数据基本不变、访问量极大，所以用「Redis 缓存 + MySQL 兜底」。缓存一旦失效或被恶意请求绕过，所有流量瞬间砸到数据库——高并发下这可能直接把 DB 打垮。经典的三个缓存问题：

- **缓存穿透**：查询**根本不存在**的数据（如恶意用 id=-100 请求），缓存永远没有，每次都打 DB；
- **缓存击穿**：某个**热点 key**（如爆款商铺）缓存到期的瞬间，大量并发同时未命中，同时回源 DB；
- **缓存雪崩**：大批 key **同一时刻**集体失效，DB 被整体冲击（对策之一是随机 TTL 分散失效时间——本项目源码未实现该方案，简历表述中已如实删除，只保留空值缓存与击穿双方案）。

针对前两个问题，项目封装了统一的 `CacheClient` 工具类：穿透用「缓存空值」防护；击穿提供「互斥锁」「逻辑过期」两种重建方案。本条简历的基线就是 500 并发击穿场景下三组方案的消融实测。

---

## 二、完整流程步骤

### 方案一：缓存空值（防穿透，`queryWithPassThrough`）
1. 请求查询商铺 → 先查 Redis `cache:shop:{id}`；
2. **命中**（有值）→ 反序列化直接返回；命中**空字符串**（""，之前缓存的空值）→ 返回错误信息「店铺不存在」；
3. **未命中** → 加互斥锁（防重建并发）→ 查 DB：
   - DB 也查不到 → 把**空字符串写入 Redis**（TTL 2 分钟）→ 返回错误。之后 2 分钟内同样的恶意请求全被这个空值挡住，不再打 DB；
   - DB 查到 → 写入正常缓存（TTL 30 分钟）→ 返回。

### 方案二：互斥锁重建（防击穿，`queryWithMutex`）——一致性优先
1. 未命中 → `SETNX lock:shop:{id}`（TTL 10 秒，防死锁）抢互斥锁；
2. **抢到锁**：再**双检查**一次缓存（防抢锁期间已被别人重建）→ 确实没有 → 查 DB → 写缓存 → 释放锁 → 返回；
3. **没抢到**：休眠 50ms 后**递归重试**整个查询逻辑 → 此时要么缓存已被重建（直接返回），要么继续等锁——总之**任何时刻只有 1 个线程在查 DB**。

### 方案三：逻辑过期（防击穿，`queryWithLogicalExpire`）——可用性优先
1. 缓存里存的不是裸数据，而是包裹对象 `RedisData{data, expireTime}`——**key 永不设置物理 TTL，靠 expireTime 字段判断逻辑过期**；
2. 请求命中缓存 → 比对 expireTime 与当前时间：
   - **未过期** → 直接返回；
   - **已过期** → `SETNX` 抢重建锁 → 抢到则提交**异步线程池任务**：查 DB + 写回新缓存（带新逻辑过期时间）+ 释放锁；抢不到或已提交 → 直接返回**旧数据**；
3. 效果：重建期间**没有任何请求被阻塞**，用户拿到的都是「可能过期的旧数据」，一致性短暂牺牲，换来所有请求秒回。

## 三、专业名词逐一解释

| 术语 | 确切含义 |
|---|---|
| **缓存穿透** | 查询的数据在缓存和 DB 里都**不存在**，每次请求都穿过缓存直达 DB（常见于恶意攻击、爬虫用不存在的 id 扫接口） |
| **缓存击穿** | 某个**热点 key** 在到期失效的瞬间，大量并发同时未命中、同时回源 DB——像在缓存上「凿了个洞」 |
| **缓存雪崩** | 大量 key **同一时刻**集体失效（如同一批 TTL 同时到期）或 Redis 宕机，DB 被整体冲击。与击穿的区别：雪崩是大面积多 key，击穿是单个热点 key |
| **缓存空值** | 对「DB 也查不到」的请求，把空字符串缓存一小段时间（本项目 2 分钟），让后续同请求在缓存层就被挡住 |
| **互斥锁（SETNX）** | `SET key value NX EX ttl`：key 不存在才设置成功——多个线程只有一个能设置成功，即抢到锁。用 Redis 实现的分布式互斥锁 |
| **锁 TTL 防死锁** | 锁设置 10 秒过期：持锁线程即使崩溃没释放，锁也会自动消失，不至于让所有请求永远等待 |
| **双检查** | 抢到锁后再查一次缓存——防止「抢锁期间别的线程已经重建完成」的重复回源 |
| **自旋重试** | 没抢到锁的线程休眠一小段（50ms）后重新走一遍查询逻辑，直到缓存被重建好直接命中返回 |
| **逻辑过期** | 缓存 key 不设物理 TTL（永不过期），把过期时间作为数据的一部分存进 value（`RedisData.expireTime`）。读取时自己判断「逻辑上是否过期」 |
| **旧数据 / 一致性** | 逻辑过期方案下，重建完成前所有用户拿到的都是过期前的旧数据——**一致性被短暂牺牲** |
| **异步重建** | 过期后由独立线程池查 DB 写新缓存，请求线程不参与重建——**可用性得到保证** |
| **DB 回源次数** | 击穿场景的核心度量：缓存未命中后实际查询数据库的次数。无防护 = 并发数；互斥锁 = 1；逻辑过期 = 1（异步） |
| **一致性 vs 可用性权衡** | 互斥锁：等重建完成才返回，数据新但请求慢；逻辑过期：立即返回旧数据但请求快——两者的取舍被本轮实测量化（270ms vs 14ms） |

## 四、如何测试验证（方法与过程）

### 4.1 测试工具与设计

- 基准脚本：`src/test/java/com/hmdp/benchmark/CacheBreakdownBenchmark.java`；
- **直接调用生产 `CacheClient`** 的三个方法（不是模拟实现），构造真实的 StringRedisTemplate 连接本地 Redis；
- 并发模型：500 个线程 `CyclicBarrier` 栅栏对齐，模拟「热点 key 失效瞬间」的请求风暴；
- 核心度量：**DB 回源次数**（在回源函数里放计数器，直接统计 DB 被查了几次）+ 单请求延迟 p50/p95 + 全部线程返回总耗时；
- 热点：店铺 ID=1（`tb_shop` 中真实数据）；每组实验前清理缓存 key 与残留锁。

### 4.2 三组消融实测数据

| 方案 | DB 回源次数 | 全部线程返回耗时 | 单请求延迟 p50 / p95 | 行为 |
|---|---|---|---|---|
| B1 无防护 | **500** | 1058ms | 992 / 1022 ms | 每个未命中线程都回源 |
| **B2 互斥锁** | **1** | 304ms | 270 / 283 ms | 仅 1 线程重建（回源时间线证实：单线程在 88ms 时刻回源），其余等缓存 |
| **B3 逻辑过期** | **1**（异步） | **48ms** | **14 / 19 ms** | 500 请求全部秒回旧数据，后台异步重建 1 次 |

### 4.3 数据解读

- **B1**：500 线程无一例外全部回源，DB 被 500 次查询瞬时冲击——单请求 p50 高达 992ms（连接池排队是主要延迟来源），这就是「击穿把数据库打崩」的量化形态；
- **B2**：回源压到 1 次——互斥锁生效；代价是其余 499 线程等待重建完成（p50=270ms），返回的是新数据；
- **B3**：所有请求 p50=14ms 秒回旧数据，重建在后台异步完成（回源 1 次）；代价是重建完成前用户拿到旧数据；
- **选型结论有了数字支撑**：一致性优先选互斥锁（新数据，p50=270ms）；可用性优先选逻辑过期（旧数据，p50=14ms，快约 19 倍）。

## 五、面试防守要点

1. **「互斥锁和逻辑过期到底怎么选？」**——看业务对旧数据的容忍度：商铺名/地址这类基本不变的数据，逻辑过期秒回体验最好；价格/库存这类强一致数据，选互斥锁。两者延迟差 19 倍是实测的；
2. **「互斥锁死锁怎么办？」**——SETNX 时带 10 秒 TTL，持锁线程崩溃锁也会自动过期，不会永久等待；
3. **「逻辑过期返回旧数据，用户发现数据错了怎么办？」**——重建在后台毫秒级完成，不一致窗口极短；对商铺档案类数据可接受；
4. **「穿透和击穿的区别？」**——穿透是「数据根本不存在」（永远 miss），空值缓存对付；击穿是「数据存在但热点 key 失效」（瞬间 miss），互斥锁/逻辑过期对付；
5. **「为什么没写随机 TTL？」**——如实说明：随机 TTL 防雪崩的思路成立，但本项目源码未实现该方案，简历不写没做的东西；雪崩的完整对策是「随机 TTL + Redis 高可用 + 多级缓存」。
