# 简历条目详解（二）：秒杀原子性（Lua 消融实测）

> **简历原文**：优惠券秒杀下单：Redis + Lua 原子合并资格校验、一人一单与库存预扣；1000 并发抢 100 件库存实测——无 Lua 的分步判断因竞态窗口受理有效率仅 10%（1000 笔全放行、库存透支 -900）、单用户重复下单 199 笔，Lua 方案 0 超卖。

---

## 一、由来背景

秒杀是电商里并发最极端的场景：100 件商品可能在 1 秒内被几万人抢。核心矛盾有两个：

1. **超卖**：库存只有 100，但订单卖出去了 1000 份——在数据库层面表现为库存被扣成负数；
2. **重复下单**：「一人一单」业务规则要求同一用户只能抢一件，但并发下「判断用户是否买过」和「记录用户已买」两个动作之间有间隙，同一个用户可能被放行多笔。

解决这两点的历史演进路线：数据库直接扣减（超卖）→ SQL 条件更新/CAS（不超卖但 DB 扛不住）→ 把「查库存、判一人一单、扣库存」三步搬到 Redis 并用 **Lua 脚本合并为原子操作**。本条简历的基线就是把「有 Lua / 无 Lua」在同一并发下做消融对比实测。

---

## 二、完整流程步骤

### 阶段一：预热（秒杀开始前）
1. 运营新增秒杀券：双写 `tb_voucher`（普通券信息）+ `tb_seckill_voucher`（秒杀配置：库存、起止时间）；
2. 把库存预热到 Redis：`seckill:stock:{券ID}` → 库存值（String）。

### 阶段二：抢购（请求入口）
3. 请求到达 → Lua 脚本以 `KEYS = [seckill:stock:{id}, seckill:order:{id}]`、`ARGV = [券ID, 用户ID, 订单ID]` 执行：
   - 校验两个 key 的 Redis 类型（防脏数据）；
   - 校验三个 ARGV 均为正整数字符串（不转 number，防大数精度丢失）；
   - 读库存：不存在 → 返回 3；非法 → 返回 4；≤0 → 返回 1（无库存）；
   - `SISMEMBER` 一人一单集合：已存在 → 返回 2（重复购买）；
   - 全部通过后才 `DECR` 库存 + `SADD` 用户——**所有判断都在任何写入之前完成**；
   - 返回 0 = 拿到资格。
4. 脚本返回 0 → 组装订单发送 RabbitMQ → 立即响应「排队中」（异步落库见详解三）。

### 阶段三：异步落库
5. 消费者收到订单 → 扣 MySQL 库存 + 插入 `tb_voucher_order`（详见详解三）。

## 三、专业名词逐一解释

| 术语 | 确切含义 |
|---|---|
| **Lua 脚本** | Redis 内嵌的脚本能力：把多条命令打包成一个脚本提交，Redis **单线程、不间断地**执行完整个脚本，期间不插入任何其他客户端的命令 |
| **原子操作** | 「要么整体执行完、执行中不被打断」的操作。Lua 的原子性指执行不被穿插——注意它**不支持回滚**：运行时错误不会撤销已执行的写入，所以脚本必须「先判断后写入」，这就是本项目把 5 类失败分支都用 `return 错误码` 提前返回的原因 |
| **竞态窗口 / check-then-act** | 「先检查条件、再执行动作」的两步之间，其他线程可以插入修改共享数据——检查时成立的条件到执行时已不成立。无 Lua 实现的三步分立判断每一步之间都是竞态窗口 |
| **一人一单** | 业务规则：同一用户对同一张券只能成功下单一次。实现：Redis Set（`seckill:order:{券ID}`）记录已购用户，`SISMEMBER` 判断、`SADD` 记录 |
| **库存预扣** | 在 Redis 层先把库存扣掉、占住名额，MySQL 的正式落库延后异步完成。预扣成功 = 拿到下单资格 |
| **超卖** | 实际卖出的数量超过库存。终态库存为负数时，其绝对值就是超卖件数 |
| **受理有效率** | 本实验定义的指标：符合业务规则的受理数 ÷ 实际受理数。多用户场景应受理数 = 库存（100）；单用户场景应受理数 = 1（一人一单） |
| **5 类返回码** | 0 成功；1 无库存；2 重复购买；3 库存未初始化；4 非法参数或 key 类型错误。所有失败都有明确编码，前端可区分提示 |
| **key 类型校验** | Lua 写入前先 `TYPE` 检查目标 key：如果库里已有同名字段但类型不对（比如库存 key 被写成了 List），直接返回 4 而不是让后续命令报运行时错误 |
| **正整数字符串校验** | 订单 ID 等大数以字符串形式校验（`string.match('^%d+$')`），不转 Lua number——Lua number 是双精度浮点，超过 2^53 会精度丢失，订单 ID 会错 |

## 四、如何测试验证（方法与过程）

### 4.1 测试工具与设计

- 基准脚本：`src/test/java/com/hmdp/benchmark/SeckillCorrectnessBenchmark.java`（JUnit 多线程基准）；
- 并发模型：`CyclicBarrier` 栅栏让 1000 个线程在同一瞬间发起（模拟秒杀开始瞬间），逐线程记录耗时；
- 场景隔离：每组实验前重置现场（Redis 库存预热 100、一人一单集合清空）。

### 4.2 四组消融

| 组 | 实现 | 场景 |
|---|---|---|
| D1a | 无 Lua：`GET` 库存 → 判断 → `DECR` + `SADD`，三步分立（复刻旧实现） | 1000 个不同用户 |
| D1b | 同上 | 同一个用户发 1000 次（验证一人一单） |
| D2a | 无 Lua（生产 `seckill.lua` 原文执行） | 1000 个不同用户 |
| D2b | 无 Lua | 同一个用户发 1000 次 |

无 Lua 实现逐行复刻了旧代码的三步逻辑：`GET` 读库存判断 → `SISMEMBER` 判重 → `DECR` + `SADD`，每步之间就是竞态窗口。

### 4.3 实测数据

| 方案 | 实际受理 | 应受理 | 终态库存 | 受理有效率 |
|---|---|---|---|---|
| D1a 无Lua·多用户 | **1000** | 100 | **-900** | **10.0%** |
| D1b 无Lua·单用户（1000 次重复请求） | **199** | 1 | -99 | **0.5%** |
| D2a Lua·多用户（生产） | **100** | 100 | 0 | **100%** |
| D2b Lua·单用户（1000 次重复请求） | **1** | 1 | 99 | **100%** |

### 4.4 数据解读

- **D1a 为什么 1000 笔全放行**：1000 个线程在扣减前读到的库存全部 >0（读-写竞态），所有人同时「检查通过」，库存被扣到 -900——900 件超卖；
- **D1b 为什么是 199 笔重复**：第一个 `SADD` 很快执行，挡住了后续大部分判断，但判断与记录之间仍有窗口，198 笔重复订单挤了进去；
- **Lua 组精确命中业务规则**：100 库存恰好 100 笔受理、单用户恰好 1 笔；
- **诚实披露**：无 Lua 墙钟反而更快（342ms vs 687ms，Lua 是串行执行 1000 次脚本，单次约 0.7ms）——用可量化的吞吐代价（+345ms）换回从 10% 到 100% 的受理正确性，这笔账是划算且必须说清的。

## 五、面试防守要点

1. **「Lua 为什么能防超卖？」**——不是 Lua 本身防超卖，是「把检查与写入合并成不被打断的原子执行」，消除了竞态窗口；数据上无 Lua 有效率 10%，Lua 100%；
2. **「Lua 会回滚吗？」**——不会，运行时错误不撤销已执行写入；所以脚本设计成「先判断后写入 + 异常用返回码表达」，从源头避免中途失败；
3. **「有效率怎么算的？」**——应受理数 ÷ 实际受理数：多用户场景应受理 = 库存 100，单用户场景应受理 = 1；
4. **「无 Lua 更快怎么解释？」**——确实更快，但快得毫无意义：省下 345ms 的代价是 900 件超卖；秒杀场景正确性 > 吞吐。
