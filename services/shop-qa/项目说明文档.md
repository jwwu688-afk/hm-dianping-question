## 1. 项目定位与整体架构

### 1.1 是什么

面向**设备说明书 / 教材手册 / 企业制度**这类非结构化文档的问答系统。用户上传 PDF 或 Markdown，系统自动解析、切分、向量化入库；之后用自然语言提问，系统检索出对应片段并生成带图片的答案。

核心业务特色是 **item_name（主体名称）贯穿全链路**：

- 导入时从文档中识别出"这部文档讲的是什么"（如 `HAK180烫金机`、`计算机网络原理`）
- 提问时先确认用户问的是哪个主体，再在该主体的范围内检索
- 这既是**检索过滤器**（`item_name in [...]`），也是**幂等覆盖写**的依据（同主体重复导入自动先删后插）

### 1.2 三进程架构

```
┌─────────────────────────────────────────────────────────┐
│  total_service.py        端口 8000                      │
│  · 只提供 app/page/index.html（统一工作台，双视图）        │
│  · 不承载任何业务接口                                     │
│  · 启动时以子进程方式拉起 8001 / 8002，退出时一并回收      │
└───────────────┬─────────────────────┬───────────────────┘
                │ subprocess.Popen    │
                ▼                     ▼
┌──────────────────────┐  ┌──────────────────────────┐
│ query_service.py     │  │ file_import_service.py   │
│ 端口 8001             │  │ 端口 8002（历史 8008）    │
│ · chat.html          │  │ · import.html            │
│ · POST /query        │  │ · POST /upload           │
│ · GET  /stream/{sid} │  │ · GET  /status/{task_id} │
│ · /history/{sid}     │  │                          │
└──────────────────────┘  └──────────────────────────┘
         │                            │
         └────────────┬───────────────┘
                      ▼
        Milvus · MongoDB · MinIO（Docker）
```

**进程管理要点**（`app/total_service.py`）：

| 机制 | 位置 | 说明 |
|---|---|---|
| 监听地址 | `:38` | `SELF_HOST = "127.0.0.1"` **写死回环** |
| 端口 | `:41-43` | `SELF_PORT=8000`（可用环境变量 `TOTAL_SERVICE_PORT` 覆盖）、`QUERY_PORT=8001`、`IMPORT_PORT=8002` |
| 子服务表 | `:46-57` | `CHILD_SERVICES` 列表，顺序即启动顺序 |
| 端口探测 | `:72-76` | 原生 `socket.connect_ex`，绕过系统代理 |
| 拉起子进程 | `:104-119` | 注入 `PYTHONPATH=项目根` + `PYTHONUNBUFFERED=1` |
| 就绪等待 | `:122-157` | 轮询最长 30s，逐个子服务打印 `[OK]` / `[FAIL]` |
| 退出回收 | `:129-147`, `atexit` | `stop_child_services()` 先 `terminate()` 再 `kill()` |

> ⚠️ **关键行为**：`start_child_services()` 会**跳过端口已被占用的子服务**（打印"已在 xxx 端口运行，跳过启动"）。
> 这意味着：**旧的 query_service / import_service 没被杀掉时，重启 total_service 不会加载新代码。**
> 排查"改了后端不生效"时，第一件事就是 `netstat -ano | findstr LISTENING` 检查 8001/8002 有没有残留进程。

## 2. 快速启动

### 2.1 前置依赖

- **Docker Desktop**（跑 Milvus / MongoDB / MinIO）
- Python 虚拟环境：`.venv`（Python 3.13.14）
- 本地模型已下载：BGE-M3、BGE-reranker-large（路径见 `.env`）
- 外网可访问：火山方舟、阿里云百炼、MinerU

### 2.2 启动步骤

**第一步 · 启动中间件容器**

容器重启策略为 `no`，**开机不会自启**，必须手动启动：

```powershell
docker start mongo minio milvus-etcd milvus-minio
Start-Sleep -Seconds 8
docker start milvus-standalone
docker ps
```

> ⚠️ **不要启动 `attu`**：它映射宿主机 8000 端口，会和工作台抢端口（当前状态就是 `Exited (1)`）。

**第二步 · 启动应用**

```powershell
cd D:\code\zgws
.\.venv\Scripts\python.exe app\total_service.py
```

等效的 `uv` 写法：`uv run python app/total_service.py`

**只调前端、不想等模型加载（约 2.5GB 内存）** 时，可跳过子服务：

```powershell
.\.venv\Scripts\python.exe app\total_service.py --no-children
```

#### ② `node_pdf_to_md` — PDF 转 Markdown

#### ③ `node_md_img` — Markdown 图片处理
`nodes/node_md_img.py:404-453`，**"五步法"**

| 步骤 | 内容 |
|---|---|
| 1 | 初始化 MinIO 客户端与 LLM 客户端 |
| 2 | 扫描 `images/` 目录，**只筛出 MD 中真正被引用的图片**（未引用的跳过） |
| 3 | 逐个调**多模态大模型**生成图片摘要 |
| 4 | 上传图片到 MinIO，把 MD 中的本地路径替换为远程 URL |
| 5 | 输出 `{原名}_new.md` |

- 支持格式（`:33`）：`.jpg .jpeg .png .gif .bmp .webp`
- 引用定位（`:72-93`）：正则 `!\[.*?\]\(.*?{filename}.*?\)`，取前后各 100 字符上下文
- 摘要提示词：`image_summary.prompt`
- **限速**（`:194-213`）：`apply_api_rate_limit(..., requests_per_minute=9, window_seconds=60)`
- 幂等（`:216-243`）：`clean_minio_directory` 先按 prefix 递归删除旧目录再上传
- URL 拼接（`:270-311`）：`{protocol}://{endpoint}/{bucket}{object_name}`，反斜杠转义为 `%5C`

#### ④ `node_document_split` — 文档切分
`nodes/node_document_split.py:337-397`，六步骤

| 参数 | 值 | 位置 |
|---|---|---|
| `DEFAULT_MAX_CONTENT_LENGTH` | 2000 | `:17` |
| `MIN_CONTENT_LENGTH` | 500 | `:19` |
| 标题正则 | `^\s*#{1,6}\s+.+` | 跳过代码块内的伪标题 |
| 切分器 | `RecursiveCharacterTextSplitter` | `:164-169` |

| `chunk_overlap` | 0 | — |

#### ⑤ `node_item_name_recognition` — 主体名称识别
`nodes/node_item_name_recognition.py:414-473`，六步骤

| 参数 | 值 | 位置 |

#### ⑥ `node_bge_embedding` — 向量生成
`nodes/node_bge_embedding.py:22-188`

### 5.4 节点详解

#### ① `node_item_name_confirm` — 确认主体名
`nodes/node_item_name_confirm.py:323-374`，五步骤

**step_1 提取**（`:21-78`）
`get_item_name_llm_client(json_mode=True)` + `rewritten_query_and_itemnames.prompt`
输出 `{"item_names": [...], "rewritten_query": "..."}`
容错：剥离 ` ```json ` 代码块、字段缺失补默认值。

**step_2 向量化检索**（`:81-158`）
对每个 item_name 单独编码 → 在 `kb_item_names` 集合做混合检索
`create_hybrid_search_requests(limit=5)`（**此处不带 expr，全库搜**）→ `hybrid_search(ranker_weights=(0.8, 0.2), limit=5, norm_score=True)`

**step_3 评分对齐**（`:161-229`）—— ⭐ **硬编码双阈值 0.85 / 0.6**

| 规则 | 条件 | 动作 |
|---|---|---|
| **A** 单高置信 | `score > 0.85` 者恰有 1 个 | 直接确认 |
| **B** 多高置信 | `score > 0.85` 者 > 1 个 | 优先取与 `extracted_name` **完全同名**的；否则取最高分 |
| **C** 中置信 | `score >= 0.6` 且无高置信 | 取 `mid[:5]` 放入 `options` |
| **D** 低置信 | 均不满足 | 无匹配 |

**step_4 三分支决策**（`:232-280`）

⭐ **动态 TopK（断崖检测）**（`step_3_topk`, `:225-271`）

| 常量 | 值 | 位置 |
|---|---|---|
| `RERANK_MAX_TOPK: int` | 10 | `:11` |

```

```

## 6. 检索链路深度解析

### 6.1 混合检索总览

```
用户提问
   │
   ├─ ① 主体名确认（LLM + kb_item_names 向量检索，双阈值 0.85/0.6）
   │       └── 得到 item_names / 或反问 / 或拒绝
   │
   ├─ ② 四路并发召回
   │       ├── 切片搜索：    rewritten_query → BGE-M3 双向量 → kb_chunks（item_name 过滤）
   │       ├── HyDE：        LLM 生成假设文档 → 拼接后 → kb_chunks（item_name 过滤）
   │       ├── 联网搜索：    百炼 MCP WebSearch（count=5）
   │       └── 图谱：        [桩] 空转 1 秒
   │
   ├─ ③ RRF 融合（k=60，两路等权 1.0，max_results=10）
   │
   ├─ ④ Rerank（BGE-reranker-large + Sigmoid + 断崖动态 TopK）
   │
   └─ ⑤ 答案生成（豆包/千问，最長 12000 字符上下文）
```

### 8.3 ⭐ item_name 命名口径（关键约定）

**入库侧与提问侧必须产出同一口径的名称**，否则查询侧的 `item_name in [...]` 精确过滤会返回 0 结果。

**统一口径规则**：

```
删除：文档类型后缀（说明书/使用手册/操作手册/学习手册/讲义/课件/
      习题集/笔记/资料/内部资料）+ 日期 + 版本号（第X版/修订版）
      + 括号内容 + 书名号 + 空格
保留：本身属于主体名的词（攻略 / 教程 / 制度 / 系统 / 原理）
```

**示例**

| 原始文件名 | 识别结果 |
|---|---|
| `计算机网络原理学习手册.pdf` | `计算机网络原理` |
| `HAK-180烫金机使用说明书.pdf` | `HAK180烫金机` |
| `日本关西旅行攻略2026-09-01_V2.0.pdf` | `日本关西旅行攻略` |
| `员工出差报销管理制度（2026修订版）.pdf` | `员工出差报销管理制度` |

### 8.4 `【图片】` 协议

`answer_out.prompt` 要求 LLM 在答案**末尾追加一个独立区块**：

```
【图片】
http://.../img1.png
http://.../img2.png
```

这是**前端硬解析的协议**：前端只渲染最后一个 `【图片】` 之前的正文，之后的 URL 单独渲染为图片网格。
⚠️ **不可改动标记或位置。**

`sse_generator` 细节：

```
① 先 yield ready
② 循环：
     await request.is_disconnected() 检测断开
     await loop.run_in_executor(None, stream_queue.get, True, 1.0)
                                       ↑ 用 run_in_executor 避免阻塞事件循环，超时 1s 静默 continue
③ 收到 __close__ → break
④ except (asyncio.CancelledError, ConnectionResetError, BrokenPipeError) → 静默退出
⑤ finally: remove_sse_queue(session_id, stream_queue)   ← 精准清理
```

> **跨线程桥接**：图在 `BackgroundTasks`（同步线程）里 `push_to_session`，SSE 生成器在 asyncio 事件循环里 `queue.get`，靠 `run_in_executor` 连接两侧。

## 13. 设计亮点

1. ⭐ **一个模型产双向量**
   BGE-M3 一次编码同时产出稠密（1024 维，HNSW/COSINE）+ 稀疏（SPARSE_INVERTED_INDEX/IP），Milvus `WeightedRanker(0.8, 0.2)` 融合，`norm_score=True` 解决量纲差异。

2. ⭐ **文本增强 + 核心词前置**
   入库前拼 `商品：{item_name}，介绍：{content}`（`node_bge_embedding.py:157`），契合并利用 BERT 架构**前 128 token 注意力集中**的特性。

3. ⭐ **item_name 作为贯穿全链路的一等公民**
   导入侧 LLM 识别 → 写 `kb_item_names` → 问答侧 LLM 提取 + 向量检索对齐（0.85/0.6 双阈值）→ 用 `item_name in [...]` 在 `kb_chunks` 上做**元数据预过滤**再向量检索 → 同时是**幂等覆盖写**的依据。

4. ⭐ **RRF + Rerank + 断崖 TopK 三段式精排**
   RRF（k=60，等权）做多路融合 → BGE-reranker-large 打分 + Sigmoid 归一化 → 相邻分数**断崖检测**（`gap >= 0.5` 或 `rel >= 0.25`）动态截断，避免机械 TopN 切断语义连续段。

5. ⭐ **MCP v1/v2 双兼容 + 手动 initialize**
   精确处理百炼服务基于 2024-11-05 协议、不支持 `server/discover` 探测的兼容问题；对 `ExceptionGroup` 做递归展开打印真实异常。

6. ⭐ **SSE 队列的竞态防护**
   `remove_sse_queue(session_id, expected)` 的 identity 校验 + `asyncio.run_in_executor` 桥接同步生产者与异步事件循环。

7. ⭐ **多供应商容错**
   `get_item_name_llm_client` 千问优先、豆包兜底；配置缺失绝不中断导入流程。

8. ⭐ **幂等性贯穿全链路**
   MinIO `clean_minio_directory` 先清后传、Milvus 按 item_name 先删后插 + `flush`、MongoDB 用 `message_id` 区分增改。

9. ⭐ **HyDE 弥合语义鸿沟**
   用 LLM 生成"假设性答案文档"再检索，让短问题与长文档在同一语义空间对齐。
